# ADR 0001: Support React 18 and React 19 side by side

-   **Status:** Proposed
-   **Date:** 2026-11-25
-   **Scope:** `@dhis2/app-platform` (cli, shell, adapter) and `@dhis2/app-runtime` (runtime, services)
-   **Depends on:** `@dhis2/ui` widening its React peer range to include `^19`

## Summary

DHIS2 apps should be able to run on React 19 without forcing every existing app to migrate at once. For a transition period, `app-platform` and `app-runtime` will support **both React 18 and React 19**:

-   React 18 stays the default for newly scaffolded apps.
-   Apps opt in to React 19 with `d2 app scripts init --react 19`, or by bumping `react` and `react-dom` in an existing app.
-   The default switches to React 19 later, once the exit criteria below are met.

This is possible because none of our libraries bundle React. They all run on the single copy of React the app installs. So most of the work is in package metadata, tooling and tests, not in runtime code.

## Background: how React reaches a DHIS2 app

To see what has to change, it helps to know where React comes from in a scaffolded app.

```
my-app/
├── package.json             ← app declares react, react-dom (installed by `init`)
├── src/App.jsx              ← app code
└── .d2/shell/               ← generated by `d2 app scripts start|build`
    ├── src/                 ← copied from @dhis2/app-shell
    └── node_modules ──────► symlink to @dhis2/app-shell's node_modules
```

-   **`init`** ([cli/src/commands/init.js](../../cli/src/commands/init.js)) installs `react@^18` and `react-dom@^18` into the app, plus `@dhis2/cli-app-scripts` and `@dhis2/app-runtime`.
-   **The shell** (`@dhis2/app-shell`) is the real entry point of every app. [bootstrapShell.js](../../cli/src/lib/bootstrapShell.js) copies its source into `.d2/shell` and **symlinks the shell's own `node_modules`** next to it. The shell renders the app's `App` component inside the adapter.
-   **The adapter** (`@dhis2/app-adapter`) and **app-runtime** (`@dhis2/app-runtime` and `@dhis2/app-service-*`) declare React as a **peer dependency**. They use whatever React the app installed.
-   **`@dhis2/ui`** is also a peer-dependent library and declares `@dhis2/app-runtime: ^3` as a peer.
-   The CLI's lockfile check ([validateLockfile.js](../../cli/src/lib/validators/validateLockfile.js)) treats `react`, `@dhis2/ui`, `@dhis2/app-runtime` and `@dhis2/d2-i18n` as **singletons**. It flags them if more than one major version is installed.

A React app must have exactly one copy of React at runtime. Two copies cause errors such as "Invalid hook call", and context values silently fail to cross the boundary.

## Problem

Today a scaffolded app cannot move to React 19:

| Blocker                                                                   | Where                                             | Effect on React 19                                                                                                                                                                                                         |
| ------------------------------------------------------------------------- | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Shell lists `react: ^18` and `react-dom: ^18` as regular **dependencies** | `shell/package.json`                              | The package manager nests a second React 18 under `@dhis2/app-shell`. Because of the `.d2/shell/node_modules` symlink, the shell renders with React 18 while the app's components use 19: two Reacts, and the app crashes. |
| `init` hard-codes `react@^18`                                             | `cli/src/commands/init.js`                        | There is no supported way to scaffold a React 19 app.                                                                                                                                                                      |
| Peer ranges cap at `^18`                                                  | `adapter`, `app-runtime` runtime and all services | npm 7+ refuses to install (`ERESOLVE`); yarn and pnpm warn.                                                                                                                                                                |
| `@tanstack/react-query@^4.36.1`                                           | `app-runtime/services/data`                       | Versions before 4.42.0 cap their React peer at 18.                                                                                                                                                                         |
| `@dhis2/ui` peers cap at `^18`                                            | external                                          | Same install failure on npm. Owned by the UI team.                                                                                                                                                                         |
| Global `JSX.Element` in published types                                   | 12 files in `app-runtime`                         | `@types/react` 19 removes the global `JSX` namespace, so our emitted `.d.ts` files break type-checking for React 19 consumers (unless `skipLibCheck`).                                                                     |
| enzyme tests                                                              | `adapter`, `shell`                                | enzyme has no adapter for React 18 or 19. These tests already run on an unsupported setup, and cannot run on 19 at all.                                                                                                    |

We also found one bug that exists today, regardless of React 19. `init` installs `@types/react` and `@types/react-dom` **without a version**, so new TypeScript apps currently get `@types/react@19` alongside `react@18`.

### What is _not_ a problem

A code audit of the cli, shell, adapter, pwa and app-runtime found **no use** of the APIs React 19 removed:

-   `ReactDOM.render` / `hydrate` (outside one example test)
-   `defaultProps` on function components
-   legacy context (`contextTypes`, `getChildContext`)
-   string refs
-   `findDOMNode`
-   `createFactory`
-   `element.ref`
-   React internals, or checks on `React.version`

The `init` templates already use `createRoot`. `@dhis2/ui` v10 only uses `defaultProps` on class components, which React 19 still supports. `styled-jsx` 4 already accepts React 19.

## Decision

### 1. Libraries support React 18 and 19 at the same time

Our libraries run on the app's React, so **library code must only use APIs that exist in both versions**. The rules for library code (`shell`, `adapter`, `app-runtime`):

-   Keep using `<Context.Provider>` (not `<Context>` as a provider) and `forwardRef` (not `ref` as a prop).
-   Do not use APIs that only exist in 19:
    -   `use()`
    -   `useActionState`, `useOptimistic`, `useFormStatus`
    -   ref cleanup functions
-   Import `act` from `@testing-library/react` or `react`, never from `react-dom/test-utils`.
-   Write types as `React.JSX.Element` (works with `@types/react` ≥ 18.2.7 and 19), never the global `JSX.Element`.

**App code has none of these restrictions.** An app on React 19 can use every React 19 feature, including `use()`, Actions, `ref` as a prop, and document metadata. That app is then simply committed to React 19.

### 2. Peer ranges

| Package                                      | New `react` / `react-dom` range                 | Release                |
| -------------------------------------------- | ----------------------------------------------- | ---------------------- |
| `@dhis2/app-runtime`, `@dhis2/app-service-*` | `^16.8.6 \|\| ^18 \|\| ^19`                     | 3.x **minor**          |
| `@dhis2/app-adapter`                         | `^18 \|\| ^19`                                  | app-platform **minor** |
| `@dhis2/app-shell`                           | `^18 \|\| ^19`, moved to **`peerDependencies`** | app-platform **minor** |

**Why app-runtime keeps React 16 in its range.** `@dhis2/ui` declares `@dhis2/app-runtime: ^3`. Removing React 16 from the range is technically a breaking change, so it would require app-runtime 4.0. Every existing `@dhis2/ui` release would then reject the new runtime. We will drop 16 (which CI has never tested) later, in a 4.0 release coordinated with the UI team.

**Why app-platform drops React 16.** The shell has depended on React 18 since v11, so no working app runs app-platform on 16. We treat this as a minor release.

**Why the shell's React becomes a peer dependency.** As a peer, the shell always uses the app's single copy of React, whatever its version. Widening the regular dependency range would usually dedupe too, but not reliably. Every real app already lists `react`, because `init` installs it. The lockfile singleton check stays in place as a safety net.

### 3. Opting in: `init --react`

```sh
d2 app scripts init my-app --react 19   # opt in
d2 app scripts init my-app              # same as --react 18 (default during transition)
```

`--react` accepts `18` or `19` and rejects anything else. It installs matching versions of `react`, `react-dom` and, for TypeScript apps, `@types/react` and `@types/react-dom`.

Existing apps opt in manually:

```sh
yarn add react@^19 react-dom@^19
yarn add -D @types/react@^19 @types/react-dom@^19   # TypeScript apps only
yarn add -D @dhis2/cli-app-scripts@latest
```

Then they run the official codemods on their own code:

```sh
npx codemod react/19/migration-recipe
npx types-react-codemod preset-19 ./src   # TypeScript apps only
```

`@dhis2/ui` must accept React 19 before this ships, so npm users do **not** need `overrides` or `--legacy-peer-deps`.

### 4. Tooling changes

-   **Babel uses the automatic JSX runtime.** [makeBabelConfig.js](../../cli/config/makeBabelConfig.js) currently uses the classic runtime plus `babel-plugin-react-require`; it moves to `@babel/preset-react` with `{ runtime: 'automatic' }`. This config drives Jest and library builds. Library builds compile file by file, so the output imports `react/jsx-runtime` and never bundles it. That import exists in React 16.14+, 17, 18 and 19, and the change avoids React 19's "outdated JSX transform" warning. The Vite path used by `--allowJsxInJs` keeps the classic runtime, as today.
-   **TypeScript template.** `tsconfig.json` switches from `"jsx": "react"` to `"jsx": "react-jsx"`.
-   **Test template.** `App.test.jsx` and `App.test.tsx` wrap `root.render(...)` in `act` from `react`. Today the test renders and unmounts without ever committing anything, so it tests nothing on either version. `act` from `react` exists in 18.3 and 19, so one template serves both.
-   **Remove enzyme.** Migrate the adapter's `ErrorBoundary` test to Testing Library, and drop the enzyme, `enzyme-adapter-react-16` and `react-test-renderer@16` dev dependencies from `adapter` and `shell`.
-   **Pin `@types/react`.** `@types/react` and `@types/react-dom` are pinned to the React major that `init` installs. This also fixes the existing type mismatch and ships first as a separate change.

### 5. app-runtime changes

-   Widen the peer ranges as in the table above.
-   Raise `@tanstack/react-query` to `^4.42.0`, the first v4 release whose peer range includes React 19. The API does not change.
-   Replace `JSX.Element` with `React.JSX.Element` in `services/offline`, `services/data` and `services/plugin`.
-   Bump `@testing-library/react` to `^16.3`, which accepts both React versions.

### 6. CI tests both React versions

Today CI is not version-aware. Both repos install from a lockfile that pins `react@18.3.1`, so a green build only proves React 18 works. The React 16 claim in app-runtime's range has never been tested.

We will add:

-   **A `test-react-19` job in each repo.** It overrides `react`, `react-dom`, `@types/react` and `@types/react-dom` to `^19` via `resolutions`, then runs build, test and type-check. In app-runtime it also checks that the emitted `.d.ts` files contain no `JSX.` references. The existing jobs keep covering React 18.
-   **An `init` smoke test in app-platform.** It runs a matrix of `{yarn, npm} × {--react 18, --react 19}`, and each run:

    1. scaffolds a throwaway app
    2. builds it
    3. asserts that only one copy of React is installed and that `.d2/shell/node_modules/react` does not exist

    This is the only test that catches the duplicate-React failure, which unit tests cannot see.

All of these jobs are required checks.

### 7. Release order

1. `@dhis2/ui` minor: peer range includes `^19` (UI team).
2. `@dhis2/app-runtime` 3.x minor.
3. `@dhis2/app-platform` minor. The shell raises its minimum `@dhis2/ui` and `@dhis2/app-runtime` versions to the releases above, so `init --react 19` can only resolve compatible versions.

The `@types/react` pin in `init` can ship before all of these.

### 8. Exit criteria: switching the default to React 19

The `init` default changes from `18` to `19` once **both** of these are true:

-   the React 19 CI jobs have been green for a full release cycle
-   at least two core DHIS2 apps run in production on React 19

The switch is a one-line change to the `--react` default plus a docs update, released as a minor.

**Why a minor and not a major.** The switch only changes what `init` writes into a _new_ app. Existing apps declare `react` in their own `package.json`, and our packages keep accepting `^18 || ^19`, so upgrading `@dhis2/cli-app-scripts` never changes an existing app's React version. `--react 18` remains available. This follows `create-vite`, which moved its React templates to React 19 without a major release. The counter-argument is that `init` output is part of the CLI's public behaviour: scripts or CI that run `init` without `--react` would start getting React 19 apps. If we decide that matters more, the switch moves to the next app-platform major after the exit criteria are met.

## Consequences

### Positive

-   Apps can adopt React 19 at their own pace, and new apps can start on it.
-   Existing React 18 apps need no changes.
-   CI covers both supported versions, and catches the duplicate-React failure mode.
-   Two existing bugs get fixed along the way: the `@types/react` mismatch in `init`, and a template test that tests nothing.

### Negative and trade-offs

-   **Library code is held to the common 18/19 API surface** until 18 support is dropped. Contributors must follow the rules in section 1.
-   **app-runtime still claims React 16 support without testing it.** That stays until a coordinated 4.0.
-   **Twice the CI time** for the React test jobs, plus the smoke matrix.
-   **Some dependencies inside `@dhis2/ui` are only _expected_ to work on 19, not declared to.** `react-popper` 2.3 is unmaintained and declares React up to 18. `react-final-form` 6 is in `@dhis2/ui-forms`, and its React 19-compatible v7 requires `final-form` 5. Both use hooks only and should work at runtime; following that up is the UI team's job.

### Behaviour that changes for apps on React 19

Nothing here breaks, but it should be documented for app developers:

-   **propTypes are ignored.** The adapter, shell and `@dhis2/ui` all use them; on 19 those runtime warnings disappear silently.
-   **Error boundaries.** Errors that an error boundary catches are no longer re-thrown to `window.onerror`; React logs them once instead. In plugin mode, the adapter's `ErrorBoundary` also calls `console.error`, so errors are logged twice. Adding `onCaughtError` and `onUncaughtError` to the shell's `createRoot` calls is a follow-up.
-   **Suspense timing.** React 19 shows a Suspense fallback straight away instead of first rendering the other components in the same boundary. The lazy-loaded `D2App` in the shell may briefly flash its loading state.
-   **Plugins.** Plugins render in their own iframe with their own React, so a host app on 18 can load a plugin on 19, and the reverse.

## Alternatives considered

| Alternative                                                         | Why we didn't choose it                                                                                                                     |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Move everything to React 19 at once (drop 18)                       | Forces every DHIS2 app to migrate in lockstep, and is blocked on `@dhis2/ui` and third-party dependencies anyway.                           |
| Make React 19 the `init` default immediately                        | It gets little real-world exercise before becoming the default. We'd rather have explicit exit criteria.                                    |
| Keep the shell's React as a regular dependency with a widened range | Deduplication then depends on how the package manager resolves versions. A peer dependency guarantees a single copy.                        |
| Release app-runtime 4.0 and drop React 16 now                       | Breaks `@dhis2/ui`'s `@dhis2/app-runtime: ^3` peer for every released UI version.                                                           |
| Keep opting in manual only, with no `--react` flag                  | It works, but gives new apps no supported way to start on 19. Once the default switches, the flag also lets people deliberately stay on 18. |
| Add a migration command (`upgrade-react`)                           | Duplicates the official React codemods; a docs page covers it.                                                                              |
| Keep the classic JSX runtime                                        | Works on 19 but may log "outdated JSX transform" warnings, and keeps `babel-plugin-react-require` around for no benefit.                    |

## Implementation checklist

**Pre-step (app-platform)**

-   [ ] Pin `@types/react` and `@types/react-dom` in `init` (`cli/src/commands/init.js`)

**app-runtime**

-   [ ] Widen peer ranges in `runtime/` and `services/*/package.json`
-   [ ] Require `@tanstack/react-query` `^4.42.0` in `services/data`
-   [ ] Replace `JSX.Element` with `React.JSX.Element`
-   [ ] Bump `@testing-library/react` to `^16.3`
-   [ ] `examples/cra`: use `useRef(null)`, bump React
-   [ ] Add a `test-react-19` job to `.github/workflows/dhis2-verify-lib.yml`

**app-platform**

-   [ ] `shell`: React moves to peer deps, raise minimum `@dhis2/ui` and `@dhis2/app-runtime`, remove enzyme and `react-test-renderer`, change `useRef()` to `useRef(null)` in `PluginLoader.jsx`
-   [ ] `adapter`: peers become `^18 || ^19`, migrate the `ErrorBoundary` test to Testing Library, delete `config/setupEnzyme.js`
-   [ ] `cli/config/makeBabelConfig.js`: automatic JSX runtime, remove `babel-plugin-react-require`
-   [ ] `cli/src/commands/init.js`: add the `--react <18|19>` option
-   [ ] Templates: `"jsx": "react-jsx"` in the TypeScript `tsconfig`, `act` in `App.test.*`
-   [ ] `examples/pwa-app`: move the test from `ReactDOM.render` to `createRoot`, bump React ranges in `examples/*`
-   [ ] Optional: remove unused `react-refresh@0.11`, `@pmmmwh/react-refresh-webpack-plugin` and `babel-loader` from `cli`
-   [ ] CI: a `test-react-19` job, plus the `init` smoke matrix (`{yarn, npm} × {18, 19}`)
-   [ ] Docs: a "Using React 19" page (opting in, codemods, the rules for library code, behaviour changes)

## Verification

-   **app-runtime:** run `yarn build && yarn test && yarn type-check` on React 18, then again with React 19 resolutions. Check that `build/types` contains no `JSX.` references.
-   **app-platform:** run `yarn test` on 18 and on 19, then run the `init` smoke matrix locally.
-   **Manual check:** in an app scaffolded with `--react 19`, run `yarn start` against a DHIS2 instance and check:
    -   header bar
    -   alerts
    -   offline and PWA install
    -   a plugin built on React 18
    -   `yarn why react` reports a single version
